System OverviewGeneral Architecture & Purpose

1.1 Description & Design Goals

TLab Monitor SRE is a next-generation self-hosted infrastructure monitoring and auto-healing system. Built on the n8n platform, the system deeply integrates an Agentic AI model capable of dynamically discovering resources, reasoning about incident root causes, and independently issuing recovery commands without hardcoding network parameters.

This open-source architecture update has entirely eliminated static IP configurations. Instead, the AI dynamically queries and injects variables (IPs, Tokens) via static mappings mapped to Environment Variables, allowing precise interaction with Docker Hosts, QEMUs, and LXCs on Proxmox.

1.2 Purpose & Roles of Core Components

The system is designed to solve end-to-end automation in server cluster management, targeting specific technologies:

  • For Docker (Container Management): When a container hangs, exhausts RAM (OOM), or stops unexpectedly, Prometheus triggers an alert. TLab Monitor automatically resolves the structure and calls the Docker Socket API to Restart/Start the container without manual intervention.
  • For Proxmox VE (PVE - Virtualization): Detects downed VMs (QEMU) or LXCs. It pairs the secure Proxmox API Token and routes REST API calls to the correct physical Node to wake up the respective VM.
  • For Agentic AI: Acts as a "24/7 Online SRE Engineer". Upon receiving metrics, the AI analyzes whether it's normal behavior (e.g., Camera system spiking CPU on motion) or a real incident. It then decides to: Ignore, Auto-Fix, or Escalate.
  • For Ntfy (Human-in-the-Loop): Creates a secure checkpoint on mobile devices. For high-risk commands impacting core infrastructure, it pushes a notification with interactive buttons (Approve / Reject). The AI is only permitted to execute upon human confirmation.

Detailed Module SpecificationsWorkflow Details

3.1 OC-3 — Agentic Monitor (The Brain)

🧠

OC-3: Agentic Monitor

Dynamic Injection · Zero-Token RAG · AI Reasoning

OC-3 represents the pinnacle of automation. Upon receiving an alert, the AI does not process "blind" strings. Instead, the Live Auto-Discovery Agent fetches the service name and reads $env variables to query Proxmox/Docker APIs in real-time.

Once located (e.g., a service at 192.168.x.x of type `container`), it injects precise parameters into the Payload. The RAG Memory system is then evaluated; if the confidence of a past solution exceeds 0.90, the AI delegates the fix to its "memory," saving 100% of tokens. Otherwise, OpenRouter AI takes over the analysis.

3.2 OC-1 — Decision Tiering & Guardrail (The Shield)

🛡️

OC-1: Decision & Guardrail

Anti Crash Loop · JSON Integrity

OC-1 halts the consequences of continuous reboot loops. Using a SQL COUNT(*) command, it counts alerts within a 10-minute window. If a Container or VM crashes ≥ 1 time in that cycle, the circuit breaker automatically trips, firing a CRITICAL notification via Ntfy to summon human help.

Furthermore, to maintain data integrity passing to the executor, OC-1 strictly wraps variables in JSON.stringify, entirely ending object formatting errors that previously crashed n8n workflows.

3.3 OC-2 — Multi-Executor & Verification (The Hand)

🤖

OC-2: Multi-Executor & Verification

Smart Sanitization · Dynamic Routing API

Static IP addresses have been completely purged from this module. Relying on metadata provided by OC-3, the execution node automatically issues HTTP Requests to the correct target environment (http://${node_ip}:2375...) accurately.

The Clean Input node acts as a final filter, employing a Regex replace(/^=/, '') to sweep invisible junk characters generated during data transit before the Switch branches out the task.

3.4 OC-4 — DB Helper & RAG Memory (The Storage)

🗄️

OC-4: DB Helper

Memory Access · Event Processing

Manages rapid retrieval via internal Webhooks. It enables the system to store resource states (CPU, Memory) in the tlab_events table, export a report of the last 20 Audit actions, and fetch the most successful remediation lessons for the AI's reference.

Safety Mechanisms & GuardrailsSystem Protection
⚠️
Resolving the n8n "JSON Render Bug"

The JSON transit error that caused incorrect Object formatting has been permanently resolved using a Wrap & Lock method:
1. In OC-1: Use JSON.stringify(...) to wrap the entire outgoing Payload.
2. In OC-2: Utilize the Clean Input Code Node with a Regex to strip invisible `=` characters.

📌
AI Hallucination Guard

The system does not grant blind control to the LLM. In the Parse AI JSON module, a hardcoded rule enforces: If the located asset is a container, the execution command is statically overridden to restart, completely blocking the AI from inventing destructive OS-level commands.
